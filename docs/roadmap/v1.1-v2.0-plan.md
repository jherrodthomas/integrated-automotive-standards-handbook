# Release Plan: v1.1 and v2.0

Status: **Draft for maintainer review** · Prepared 2026-10-14 · Baseline: v1.0.0 (ISH-2026-001 Rev A, 166 pp.)

This plan turns the README roadmap into scoped, reviewable work. It has three inputs:

1. The v1.1 and v2.0 items already listed in `README.md` and `CHANGELOG.md`.
2. A read-through of v1.0, with a close look at Chapter 8 (Software & AI/ML Development). It turned up errata and coverage gaps, listed in §2.
3. An offer from an external practitioner (Core OS team, Android Automotive OS and QNX) to review drafts of the software chapters. §5 sets up a reviewer program so this and later offers have a clear path to follow.
4. Reader feedback asking for STPA, and the maintainer's companion project [LionDriver](https://github.com/jherrodthomas/LionDriver), which already applies the handbook's integrated approach to a real open-source driving stack. §4.5 and §4.6 cover these.

The main change from the README roadmap: **v1.1 becomes the accuracy and software-platform release.** "Expanded worked examples and diagrams" stays in v1.1, but only after the errata and the Chapter 8 rework. A handbook that practicing engineers cite has to get its clause references right first.

## 3. Enabler: reviewable source (do first)

Line-level review needs text under version control. Options:

| Option | Pros | Cons |
|---|---|---|
| **A. Markdown + Pandoc (→ PDF via LaTeX/Typst)** | GitHub renders it, PR line comments work, the web explorer (v2.0) can reuse it | Complex tables need care. 109 tables to convert |
| B. LaTeX source in repo | Matches current typeset quality | Harder for casual contributors. GitHub doesn't render it |
| C. Keep PDF-only; review through issues | Zero migration cost | Reviewers comment on page numbers. Doesn't scale |

**Recommendation: A, done one chapter at a time.** Convert Chapter 8 first, so the software review can run on it right away, then the remaining chapters through v1.1. Cross-mapping tables can go in as CSV/YAML under `data/` and be rendered into the book. That same dataset becomes the backend for the v2.0 explorer, which saves building it twice.

Proposed layout:

```
src/chapters/08-software-ai.md
data/crossmap/*.yaml        # Rosetta Stone rows: activity -> {standard: clause}
data/errata.yaml            # tracked corrections, rendered into an errata appendix
build/                      # pandoc config, templates
```

A CI check can then lint clause-reference formats, flag any `Cl.x.y` that isn't in a known-structure list per standard, and catch stats drift (E12).

## 4. v1.1 content scope

### 4.1 Chapter 8 rework: "Software & AI/ML Development"

Today's Chapter 8 reads as application-level coding guidance (MISRA, coverage, fuzzing) plus the AI/ML lifecycle. It has nothing on **platform software**: operating systems, hypervisors, middleware, and the place where ISO 26262 and ISO/SAE 21434 actually meet in a modern vehicle computer. The v1.0 text has zero mentions of hypervisors, freedom from interference, SEooC, QNX, Android, Linux, or open source. Proposed new structure (new or substantially rewritten sections in **bold**):

| § | Title | Notes |
|---|---|---|
| 8.1 | Phase overview | Fix clause map (E2) |
| 8.2 | Standard-by-standard requirements | Re-map table (E2, E7, E8) |
| **8.3** | **Platform software as a safety & security element** | OS/RTOS, hypervisor, middleware (AUTOSAR Classic/Adaptive, SOME/IP, DDS) as Safety Element out of Context (26262-10 Cl.9) and as an out-of-context cybersecurity component (21434). The assumptions of use that each side hands to the integrator, and why the two sets of assumptions must be reconciled. |
| **8.4** | **Freedom from interference & mixed-criticality partitioning** | 26262-6 Annex D (timing, memory, information exchange) and 26262-9 Cl.6 (coexistence criteria). Patterns: MPU/MMU separation, temporal partitioning, safety-certified RTOS hosting ASIL functions next to QM rich OS (e.g., Android Automotive OS) in a separate VM, IPC and shared-memory channels between criticalities. The same partition boundary is also a **security trust boundary**: one design argument, two standards. |
| **8.5** | **Where 26262 meets 21434 at the platform level** | Secure/measured boot chain, memory protection, watchdog/health monitoring, update and rollback. For each mechanism: which safety goal and which cybersecurity goal it serves, where they conflict (e.g., fail-safe vs. fail-secure, crypto latency vs. FTTI, debug access), and how to record the trade-off. Builds on 26262-2 Annex E (safety–security interaction) and 21434 Cl.5/Cl.10. |
| **8.6** | **COTS and open-source software** | 26262-8 Cl.12 (qualification of SW components) and Cl.14 (proven in use) vs. what is realistic for Linux/AOSP-scale code. 21434 view: off-the-shelf components, SBOM, vulnerability monitoring (Cl.8). The patch-cadence vs. re-qualification problem leads into ISO 24089 in v2.0. |
| 8.7 | Coding standards convergence | Rebuilt MISRA/CERT table (E3–E5). Add MISRA C++:2023 / AUTOSAR C++14 for Adaptive/platform C++ code. Add a short note on Rust (ISO 26262 tool-qualification status of Rust toolchains) |
| 8.8 | Unified verification methods matrix | Fix coverage (E1, E6). Add platform-level verification: FFI evidence (WCET/timing analysis, fault injection across partitions), and interface fuzzing of IPC/hypervisor calls |
| 8.9 | AI/ML lifecycle | Re-verify 8800 refs (E8). Add a deployment subsection: inference runtime on the platform (GPU/NPU drivers as safety-relevant dependencies) |
| 8.10 | Commonality / gap analysis | Update with platform rows |
| 8.11 | Integrated checklist & work products | Add platform SEooC assumption register, FFI analysis, safety–security trade-off log |
| 8.12 | Worked mini-example | Keep AEB SW unit. **Add a second mini-example: an ASIL B instrument-cluster telltale rendered next to a QM Android Automotive IVI on one SoC through a hypervisor.** This previews the v2.0 worked example. |

Authoring guidance for these sections:

- Stay vendor-neutral in normative text. Name products (QNX, AAOS, specific hypervisors) only as illustrative examples, with no claims about any vendor's certification status unless public and cited.
- Every claim of the form "standard X requires Y" carries a clause or RQ reference. Everything else is labeled practice or example.

### 4.5 STPA (reader request; moved forward from v2.0)

v1.0 organizes the concept phase around the "Big Four" analyses (HARA, TARA, SOTIF, AI hazard analysis). All four start from either component failures or a list of threats or triggering conditions. STPA starts from the control structure and finds hazards that come from unsafe *interactions*: mode confusion, a driver who stops supervising, two controllers fighting over the same actuator. Those are the gaps an integrated handbook should cover.

Where it goes:

| Location | Content |
|---|---|
| Ch. 2 | Short profile: STPA (Leveson & Thomas, *STPA Handbook*, 2018), four steps, and where the standards accept it. ISO 21448:2022 names system-theoretic methods for hazards from functional insufficiencies and foreseeable misuse. ISO 26262 allows it as a supplementary system-level analysis. SAE J3187 applies it to cybersecurity (v2.0). Clause numbers to be verified. |
| Ch. 3 | Add STPA to the standards interaction map as a method that feeds several standards at once, not a seventh standard |
| Ch. 5 | New §5.x "STPA as the integrating analysis". Shared losses and system-level hazards with the HARA, so STPA results trace to the same safety goals. Unsafe control actions → SOTIF triggering conditions, misuse cases, FSC requirements. A Rosetta Stone row for STPA artifacts (losses, hazards, constraints, control structure, UCAs, loss scenarios) mapped to 26262 / 21448 / 21434 / 8800 work products. |
| Ch. 5 §5.8 | Add STPA steps 1–2 to the AEB mini-example |
| Ch. 13 | Fold STPA outputs into WP-2 (integrated risk assessment) instead of a new standalone document |

Source material: LionDriver's [WP-A-05 STPA](https://github.com/jherrodthomas/LionDriver/blob/liondriver-dev/assurance/08-analyses/WP-A-05-stpa.md) has all four steps for a supervised L2 system. It reuses HARA hazards H-01…H-08 as STPA system-level hazards. It found one hazard the HARA had folded into others (H-STPA-1, driver not supervising), which was then decided into the HARA and SOTIF misuse analysis. That is the "STPA finds what failure-based methods miss" story the chapter needs, with a real trace behind it. It also leaves attackers out of scope and defers them to the TARA, which sets up the v2.0 J3187 section.

### 4.6 LionDriver as the companion reference implementation

The handbook says what the six standards ask for. [LionDriver](https://github.com/jherrodthomas/LionDriver) (an openpilot derivative, same maintainer) shows what the integrated work products look like when they are actually written for a real system: about 80 work products laid out by lifecycle phase, trace data, a living safety case with claims, evidence and open defeaters, and change impact records tied to commits. It is proof that the handbook's approach can be practiced, not only described.

How to reference it:

| Handbook location | LionDriver work product | Shows |
|---|---|---|
| Ch. 3 / Ch. 13 | `assurance/` tree, work product register (WP-M-00) | An integrated work product set organized by phase, as Ch. 13 recommends |
| Ch. 5 | WP-C-03 HARA, WP-C-06 SOTIF, WP-C-09 TARA, WP-C-11 AI safety requirements, WP-A-05 STPA | The Big Four (plus STPA) on one item with shared hazards |
| Ch. 8 §8.4 | WP-A-02 coexistence & freedom from interference | Doer/checker: a learned driving stack on a rich OS, gated by a small deterministic checker on a safety MCU. A real mixed-criticality FFI argument (26262-9 §6, 26262-6 Annex D) |
| Ch. 8 §8.6 | WP-M-11 upstream & supplier management, WP-P-08 SW component qualification, WP-P-09 proven in use | The COTS / open-source problem in its hardest form: inheriting a large upstream codebase |
| Ch. 8 §8.8 | WP-W-06…08, CI safety workflow (coverage gate, MISRA, mutation testing) | Verification automated in CI |
| Ch. 8 §8.9 | WP-W-10 ML engineering | 8800-informed ML engineering for an end-to-end driving model |
| Ch. 9 §9.6 | `assurance/case/`, WP-K-01 safety case, GSN | Living assurance case with defeaters, generated and checked in CI |
| Ch. 10 | `07-supporting/impact/`, field monitoring case FI-2026-001 | Per-change impact analysis and a field-monitoring RCA |

Rules for these references, so the book stays credible:

- **State the status honestly.** LionDriver's own records say its work products are drafts, many AI-assisted, with no accepted evidence yet, and that it claims no compliance or certification. The handbook must say the same. Use "illustrates" or "example of", never "compliant" or "certified".
- **Pin to a release or commit**, not the moving `liondriver-dev` branch, so a reference printed in v1.1 still points to the text it described. Cut a LionDriver tag for each handbook release.
- **Keep the handbook self-contained.** Each reference is a sidebar ("See it in practice: …") next to content that stands on its own. No chapter should need LionDriver to make sense.
- **Disclose the relationship.** One line in Ch. 1: LionDriver is maintained by the handbook's author.
- **Feedback runs both ways.** Errors the handbook review finds in LionDriver go back as LionDriver issues, and vice versa.

The v1.2 filled-in templates can start from LionDriver work products (generalized away from the Corolla reference vehicle) instead of being written from scratch.

## 5. Reviewer program

Without a defined process, offers to review get lost. Proposed setup:

**Roles**

| Role | Commitment | Credit |
|---|---|---|
| Chapter reviewer | One or two chapters per release. Technical accuracy, clause verification, practitioner realism | Named in Acknowledgments and `CONTRIBUTORS.md` |
| Proofreader | Language, consistency, acronyms, cross-references | Named in Acknowledgments |
| Clause verifier | Has a licensed copy of a specific standard. Confirms references only | Named per standard |

**Process**

1. Draft chapter opened as a PR (Markdown source, §3) labelled `review-requested`, with a review packet. The packet holds the scope, the specific questions for the reviewer, the standards in scope, and a deadline (typically 2–3 weeks).
2. Reviewers comment inline on the PR. Anyone who prefers not to use GitHub can use the annotated PDF + the **Draft Review** issue template.
3. Each comment gets one of: *accepted*, *accepted with change*, *deferred (issue #)*, *declined (reason)*. The maintainer closes the loop before merge.
4. A release candidate (RC) PDF goes to all reviewers for a final week before tagging.

**Ground rules (put in CONTRIBUTING.md)**

- Reviewers take part **in a personal capacity**. Comments must not contain employer-confidential or proprietary information, and appearing in the Acknowledgments does not imply endorsement by any employer.
- No verbatim standard text (current CONTRIBUTING rule).
- Contributions are licensed under the repo license (H1 must be settled first).

**First assignment (proposed)**

| Reviewer background | Assignment | Timing |
|---|---|---|
| Core OS: Android Automotive OS + QNX | Chapter 8 §8.3–8.6 and the cluster/IVI mini-example (8.12), first draft. Then a proofread of the whole of Chapter 8 at RC. | Draft to reviewer ~2026-11-15, comments by ~2026-12-06 |

Specific questions to put to that reviewer:
- Does the FFI / mixed-criticality section match how a safety-certified RTOS and a QM rich OS are actually partitioned and argued on current cockpit SoCs?
- Where do 26262 SEooC assumptions and 21434 out-of-context assumptions conflict in platform practice?
- Is the COTS/open-source section realistic about what can be claimed for AOSP/Linux-scale code?
- What is missing that a platform engineer would expect to find?
- Does LionDriver's FFI analysis (WP-A-02) work as a "see it in practice" example for §8.4, or is it too far from a production cockpit SoC?
